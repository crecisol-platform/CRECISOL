Sin sesión real, roles productivos, DB real de permisos o acceso a datos privados.

- `Domain/Tenancy/TenantBranchResourceScope.cs`: tipos opacos `TenantBranchId` y `TenantResourceId` no vacíos; clave de acción `TenantRequiredAction` canónica ASCII en minúsculas (`module.action` o `module.subject.action`) definida **solo por política del backend**, sin roles/sectores hardcoded; `TrustedBranchResourceSnapshot` de catálogo protegido con `TenantId`, `BranchId`, `ResourceId`, `OwnerActorId`, estado de recurso Active/Suspended/Deleted y estado independiente de sucursal Active/Suspended/Deactivated, cada cual con revisión y timestamp UTC procedente de futuro JOIN de catálogo protegido por tenant; sucursal suspendida o deactivated bloquea incluso si el recurso permanece Active; `TrustedActorBranchGrantSnapshot` con `ActorId`, tenant, branch, acción, alcance `OwnerOnly` o `BranchWide`, estado Pending/Active/Suspended/Revoked, revisión y vencimiento UTC; evidencia tipada `TenantBranchResourceScopeEvidence`, con revisiones e IDs opacos, NO credencial/bearer ni acceso a datos.
- `Application/Tenancy/ResolveCurrentBranchResourceScope.cs`: usar **primero** `ResolveCurrentTenantIdentityContext.ExecuteAsync` de C04-05; no aceptar identidad/tenant/sucursal/rol/host/claims del cliente; buscar recurso por `TenantId` autorizado + `TenantResourceId` únicamente como **selector no autorizante**; rechazar recursos de otro tenant/ID, suspendidos y metadata futura. Consultar **todas** las concesiones exactas por actor+tenant+branch+acción; cero, nulo o duplicado = rechazo; comprobación de los cuatro campos, revisión, vigencia UTC; `OwnerOnly` exige `OwnerActorId == ActorId`, `BranchWide` solo con concesión explícita de esa sucursal y acción, nunca heredar de A→B. Releer recurso (incluyendo estado/revisión propia de sucursal), concesiones, y **re-ejecutar identidad C04-05** antes de devolver evidencia para detectar cambios de revisión/branch/owner/acción/sesión/host. Reloj backend UTC validado tras esperas; cancelación antes y después de cada consulta.
- `ITrustedTenantScopedResourceReader`: solo metadatos internos, lookup con **ambos** tenant y resource ID, NO contenido privado/DSN.

**NO se modela un bypass SuperAdmin.** Si requiere inspección de datos privados, una autorización excepcional futura con MFA, motivo, caducidad y auditoría seguirá siendo obligatoria. Los records son snapshots de **catálogo confiable supuesto**: un atacante puede construir tipos en tests, pero ninguna API los acepta o confía en cliente.

## 3. Matriz obligatoria de pruebas

Positivos: actor A con identidad y membresía A vigente, recurso de branch A, concesión exacta y vigente OwnerOnly con dueño A; otro actor con concesión BranchWide explícita para branch A; dos sucursales A/B del mismo tenant con concesión SOLO en una; diferentes tenants A/B; acciones parametrizables explícitas `case.read` y `case.update`, ambas requieren grant propio.

Negativos P0: recurso B (tenant o branch), identidad ajena, grant de actor B, branch B, tenant B, acción distinta, grant duplicado, grant del mismo actor y branch pero de `OwnerOnly` sobre recurso de otro owner, recurso suspendido/deleted, sucursal suspendida/deactivated o con revisión/estado alterados durante la consulta, grant pending/suspended/revoked, expiración exacta, fecha futura, IDs vacíos, action key con URL/espacios/Unicode/inyección/comodín; datos de catálogo de otro tenant/ID, revocación entre dos lecturas, cambio branch/owner, grant cambia de modo/revisión/acción, identidad host cambia durante operación; no fallback a privilegio global/administrador o a branch sin referencia.

Negativos P1: cancelación antes de identidad, tras recurso, tras grant, tras relectura y antes de emitir evidencia; errores de puertos que deben propagarse con denegación; reloj no UTC; revisión cero/negativa; no logs de IDs, permisos, datos ni DSN; no rutas ni DI privadas.

**Límite temporal:** revalidación de snapshots mitiga carreras durante el cálculo, pero **NO garantiza atomicidad** ante revocación posterior: la operación de datos deberá acoplar la comprobación al uso de recurso por query/transaction con filtros `tenant_id + branch_id + resource_id + owner_id` y control de revisión en futuras microfases. Un resultado de C04-06 **no autoriza por sí solo** leer/escribir, exportar, ver medios, cachear, iniciar jobs o seleccionar DB. C04-11 tendrá que probar BOLA/IDOR HTTP y SQL de punta a punta.
