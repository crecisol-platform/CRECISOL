# C05 — Prueba unificada de registro neutral y posesión de buzón (aislada)

**Fecha:** 2026-11-14. **Alcance:** solo ensayo loopback ASP.NET Core 10 con MySQL 8.4 descartable, sin endpoints privados en `Crecisol.Api/Program.cs`. PR de trabajo #151, expediente #150.

## Camino comprobable en un mismo proceso

`POST /__test_only/c05-integration/registration-intent` valida transporte y JSON antes de invocar el caso de uso y el procedimiento MySQL de ingesta neutral. En las pruebas históricas, el identificador se obtenía exclusivamente por el lector SQL protegido; el corte de despacho automatizado reemplaza esta dependencia usando una cola transaccional interna. La misma aplicación de ensayo ejecuta `POST /__test_only/c05-integration/proof-request` y `POST /__test_only/c05-integration/proof-confirm`, usando `VerifyNeutralRegistrationMailbox`, `MySqlDisposableEmailPossessionAdapter` y un buzón simulado que no puede entregar fuera del proceso. El comprobante del cliente es siempre neutral; no se crea ninguna cuenta **activa**, rol, membresía, sesión ni privilegio; el ensayo puede crear un **candidato pendiente** tras prueba de buzón.

La cadena se prueba con un solo contenedor MySQL descartable y tres fixtures SQL ya existentes: tenants/invitaciones, ingesta y proof CAS. La CI específica ejecuta el script `database/tests/c05_identity_neutral_proof_http_mysql.sh` y exige evidencia sobre el mismo SHA de GitHub y el mismo run.

**Seguridad comprobada mediante casos ejecutables:** host B no accede a tenant A; el token de B usado en A no verifica; desafío incorrecto o reutilizado no cambia el estado; prueba auténtica cambia PENDING a VERIFIED exactamente una vez; JSON duplicado, selector de tenant, encabezados actor/Forwarded, host no verificado y campo mailbox introducido en la confirmación se deniegan antes de la llamada protegida. El correo, token y claves no se escriben en los logs.

**Importante:** este flujo prueba **posesión de buzón sintética por canal loopback** y creación transaccional de **credencial Argon2id PENDING_MEMBERSHIP** sin privilegios. No prueba proveedor SMTP real, aprobación de membresía/realm, MFA, login contextual, emisión y revocación de sesión, rate limit compartido con login, autorización por tenant/sucursal/recurso ni frontend Angular privado. A/B/C del capítulo completo siguen pendientes; C06 permanece BLOQUEADO. No atribuir `success` al nuevo corte antes de leer la CI final. `dev`, `main`, producción, Documento Maestro Único y SOLQARYN no se alteran.

## Extensión P0 — identidad global pendiente y colisiones

`MySqlDisposableVerifiedCredentialCandidateStore` recupera exclusivamente el buzón cifrado del intent verificable, valida AES-GCM y liga el digest de correo al mismo tenant/intent en la transacción MySQL. Un digest HMAC de la clave de login (normalización explícita del login C05-04) tiene índice único **global**; dos buzones de diferente capitalización que colisionen nunca se fusionan ni obtienen dos actores. El procedimiento requiere tenant ACTIVO, intent vigente, proof VERIFIED, PHC Argon2id y crea solo `PENDING_MEMBERSHIP`, sin tabla de grants o sesiones. El rol SQL no puede leer directamente verificadores. Las pruebas específicas verifican 12 competidores (1 ganador), replay, falta de proof, cruce de tenant, lectura prohibida y colisión de identidad con buzón verificado por separado.

**Evidencia:** no atribuir PASS al último SHA hasta comprobar CI sobre él. La suite no incluye servicio productivo de contraseña comprometida (el filtro test-only acepta secretos sintéticos), correo real ni alta de usuario habilitado. Persistencia de candidatos es un **fixture descartable**, no migración de producción. A/B/C integrales de todo C05 continúan PENDIENTES y C06 BLOQUEADO.

## Corte siguiente — despacho servidor→buzón sin identificador privilegiado en el navegador

El nuevo archivo `database/tests/fixtures/c05_02_neutral_dispatch_fixture.sql` define una **cola MySQL de prueba** con trigger `AFTER INSERT` sobre la intención protegida. La operación de registro y el encolado quedan dentro de la misma transacción; un rechazo por cuota o tenant suspendido no agrega una entrega. `MySqlDisposableNeutralProofDispatch` no admite tenant, mailbox, credencial ni intent desde HTTP: reclama un único par `(tenant,intent)` verificado desde SQL mediante `SELECT ... FOR UPDATE SKIP LOCKED` y una concesión `EXECUTE` sin `SELECT` sobre buzones. Una concesión de propietario con caducidad controla reintentos y la confirmación de emisión CAS, sin aceptar propietario vencido ni tenant diferente.

La prueba unificada ejercita un flujo que **no depende de leer el identificador con la conexión de setup**: el usuario anónimo recibe solo `ACK`; el worker interno obtiene su propio par opaco del outbox, resuelve el Host desde el catálogo de prueba, inicia la verificación y entrega el `intentId` junto con el secreto **solo al buzón local protegido**. Al simular la confirmación del destinatario se valida el par tenant + intent + desafío y se crea únicamente una credencial candidata `PENDING_MEMBERSHIP` con Argon2id. Pruebas ofensivas: reclamaciones paralelas, segundo worker sin trabajo, titular de lease falsificado o vencido, procesamiento único, tenant A con enlace de B, repetición de secreto, operación SQL sin derechos de lectura y ausencia de nuevas sesiones o roles.

**Límites que siguen abiertos:** el worker demostrado vive solamente en `backend/tests`, y el buzón y el enlace se simulan localmente; todavía no existe proveedor real SMTP, catalogo de almacenamiento production/shared-dedicated, workflow operativo de activación de membresía, login pre-autenticación con acceso contextual privado, MFA/step-up combinado con sesión revocable, recuperación asociada ni autorización backend de recurso/sucursal. Las nuevas pruebas de despacho requieren `completed/success` sobre el SHA final para acreditarse. Esta no es una migración operativa, ni activa C06.

**Rollback del corte de despacho:** revertir el trigger/tabla/procedimientos del fixture descartable, `MySqlDisposableNeutralProofDispatch`, la extensión opcional del sink, el runner y su CI, sin modificar Word/PDF, la ruta `Program.cs` de producto ni `main`.

## Corte adicional — aprobación independiente y preparación contextual de login

El fixture nuevo \`database/tests/fixtures/c05_02_membership_approval_fixture.sql\` separa expresamente **identidad candidata pendiente**, **autoridad de aprobación** y **membresía**. Un correo verificado y un PHC Argon2id por sí solos no activan la identidad. Los registros del aprobador y la orden se introducen únicamente por el **setup privilegiado del entorno descartable**, como simulación sintética de evidencia independiente de sesión+MFA; los trabajadores de activación solo reciben \`EXECUTE\` sobre \`c05_02_activate_approved_candidate\`, sin \`INSERT/UPDATE/SELECT\` de aprobaciones, PHC ni membresías.

El procedimiento SQL revalida tenant activo, candidato pendiente del mismo tenant, proof de buzón verificada recientemente, aprobador distinto del candidato y orden no consumida, con revisión exacta de sesión y MFA, caducidades estrictas y bloqueo de filas. La membresía generada carece de roles, permisos de acción o sesión. \`MySqlDisposableApprovedLoginDirectory\` consulta únicamente el índice global HMAC y vinculación de membresía mediante usuario SQL de solo lectura. El caso de uso existente \`PrepareContextualPasswordLogin\` valida hash **Argon2id real**, Host B verificado, identidad activada y enlace B fresco; antes de la aprobación, después de revocación, con contraseña incorrecta, actor desconocido, Host A, aprobación vencida o alterada, devuelve denegación y no emite bearer.

La suite adicional \`LocalApprovedMembershipHarness\` ejecuta negativas por usuario y tenant, las revisiones de sesión/MFA sintéticas revocadas o no coincidentes, doce activaciones simultáneas (una sola ganadora), replay de aprobación, lectura y mutación prohibidas a los respectivos roles SQL, y revocación posterior. Debe verificarse \`completed/success\` sobre el SHA exacto final antes de atribuirle aprobación.

**Importante: esto NO es activación real de operadores/MFA, ni inicio de sesión del producto.** El setup simula la aprobación privilegiada; todavía NO existe un circuito productivo que autentique al aprobador, pruebe MFA, emita sesión o autorice recursos. La preparación de C05-04 no es permiso para endpoints, y la API pública no registra nuevos endpoints de identidad. El workflow de capítulo completo sigue bloqueado por rate limit antes del hash en el mismo camino, MFA/step-up real, sesiones CAS, recuperación, propiedad de recursos y pruebas Angular privadas.
